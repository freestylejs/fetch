## Overview

The OpenAPI Generator splits the client across separate surfaces: pure TypeScript
types, Zod-backed runtime validators, and the router/auth bindings that connect them.
This separation keeps type checking fast while preserving full runtime validation.

## File Structure

### A. types.ts

Contains pure TypeScript type aliases derived from your OpenAPI components — no runtime
code, no imports:

- **Type exports** - One `<Name>Model` alias per component schema
- **No validation** - Types only; validators live behind the schemas surface

```typescript
export type UserModel = {
  id: string
  username: string
  email: string
  createdAt: string
}
```

### B. schemas.js / schemas.d.ts

`schemas.js` contains the runtime validators built from your OpenAPI components:

- **Parsers** - An exported `parse<Name>` function per schema and operation validator
- **Zod-backed** - Each parser validates data at runtime before returning it typed

`schemas.d.ts` is its declaration pairing, so TypeScript programs see only the parser
signatures and the types they return.

```typescript
// schemas.js — plain JavaScript, not part of type checking
import { z } from 'zod'

const User = z.object({
  id: z.string(),
  username: z.string(),
  email: z.email(),
  createdAt: z.iso.datetime()
})

export const parseUser = (value) => User.parse(value)
```

```typescript
// schemas.d.ts — what consumers' compilers resolve
import type { UserModel } from './types'

export declare const parseUser: (value: unknown) => UserModel;
```

### C. domains/`<segment>`.ts + api.ts

For every top-level path segment the generator emits one **plain structure
module** under `domains/`. Each module exports an uncompiled object literal —
`f.builder()` chains bound to `Schemas.*` parsers, nothing else:

```typescript
// domains/users.ts (generated)
import { f } from '@freestylejs/fetch'
import * as Schemas from '../schemas'

export const usersDomain = {
    users: {
        $userId: {
            GET: f.builder()
                .def_json()
                .def_response(async ({ json }) => Schemas.parseUser(await json()))
        }
    }
}
```

`api.ts` stays the single entry point and composes the domain structures via
spread. Spreading is pure structural composition, so your editor resolves
exactly the same client type as a single inline tree:

```typescript
// api.ts (generated)
import { f } from '@freestylejs/fetch'
import { usersDomain } from './domains/users'
import { billingDomain } from './domains/billing'
import { createAuthMiddleware, AuthConfig } from './auth'

export const createClient = (config: { baseUrl?: string, auth?: AuthConfig } = {}) => {
    const authMw = config.auth ? createAuthMiddleware(config.auth) : undefined
    const middleware = authMw ? authMw : []

    return f.router({
        baseUrl: config.baseUrl || 'https://api.example.com',
        middleware
    }, {
        ...usersDomain,
        ...billingDomain
    })
}
```

- **Base URL** - Extracted from `servers[0].url` in the specification (server variables resolved)
- **One domain per top-level segment** - Large specs split into navigable files; single-segment specs emit one domain module
- **Type inference** - Full TypeScript support for all operations

Inline schemas (query parameters, inline request/response bodies) are automatically
promoted into named parsers on the schemas surface — generated router files never
contain raw Zod expressions.

:::tip
The exported domain structures are plain objects, so you can recompose them with
`f.compose(config, ...structures)` to build custom clients from parts of a
generated API.
:::

### D. auth.ts

Contains type-safe authentication configuration and middleware factory:

- **AuthConfig** - Interface matching your OpenAPI security schemes
- **Middleware Factory** - Creates authentication middleware based on config
- **Supported Schemes** - Bearer, Basic, API Key, OAuth2

Example generated auth:

```typescript
import { f, type Middleware } from '@freestylejs/fetch'

export interface AuthConfig {
    /** Bearer authentication */
    bearerAuth?: {
        token: string | (() => Promise<string>)
    }
    /** API Key authentication */
    apiKey?: {
        value: string | (() => Promise<string>)
    }
}

export const createAuthMiddleware = (config: AuthConfig) => {
    const middlewares: Middleware[] = []
    // ... middleware implementation
    return middlewares
}
```

### E. index.ts

Re-exports all generated code:

```typescript
export * from './api'
export * from './types'
export * from './schemas'
export * from './auth'
```

## Usage Patterns

### A. Client Initialization & Authentication

The generated code exports a `createClient` factory function that allows you to configure the base URL and authentication credentials.

```typescript
import { createClient } from './api'

// Initialize with auth configuration
const client = createClient({
  baseUrl: 'https://api.example.com', // Optional override
  auth: {
    // Type-safe config based on your OpenAPI security schemes
    bearerAuth: {
      token: 'my-secret-token'
    },
    apiKey: {
      // Supports async functions for token rotation
      value: async () => await getApiKey()
    }
  }
})

// Use the authenticated client
const user = await client.users.me.GET.query()
```

### B. Path Parameters

Dynamic path segments use the `$paramName` syntax:

```typescript
// OpenAPI: /users/{userId}
// Generated: client.users.$userId

const user = await client.users.$userId.GET.query({
  path: { userId: '123' }
})
```

### C. Query Parameters

Query parameters are validated by promoted parsers on the schemas surface:

```typescript
// OpenAPI: /users?page=1&limit=10
// Generated with searchparams

const users = await client.users.GET.query({
  search: {
    page: 1,
    limit: 10
  }
})
```

### D. Request Bodies

Request bodies are validated against the generated parsers:

```typescript
// OpenAPI: POST /users with body
// Generated with def_body

const newUser = await client.users.POST.query({
  body: {
    username: 'john',
    email: 'john@example.com'
  }
})
```

### E. Response Validation

Responses are automatically validated:

```typescript
// Response is validated at runtime before being returned
const user = await client.users.$userId.GET.query({
  path: { userId: '123' }
})

// TypeScript knows the exact shape
user.username // string
user.email    // string
```

## Type Inference

The generated client provides complete type inference:

### A. Request Types

```typescript
// TypeScript infers the shape of path params, search params, and body
client.users.$userId.GET.query({
  path: { userId: '123' },   // Type: { userId: string }
  search: { include: 'posts' } // Type: { include?: string }
})
```

### B. Response Types

```typescript
// Response type flows from the schemas surface declarations
const user = await client.users.$userId.GET.query({
  path: { userId: '123' }
})

// user: UserModel
```

You can also reference model types directly:

```typescript
import type { UserModel } from './types'
```

## Schema Conversion

The generator converts OpenAPI types to Zod schemas:

| OpenAPI Type | Zod Schema | Example |
| ------------ | ---------- | ------- |
| `string` | `z.string()` | `"hello"` |
| `number` | `z.number()` | `42` |
| `integer` | `z.number().int()` | `10` |
| `boolean` | `z.boolean()` | `true` |
| `array` | `z.array(...)` | `[1, 2, 3]` |
| `object` | `z.object({...})` | `{ key: "value" }` |
| `string` (format: date-time) | `z.iso.datetime()` | `"2024-01-01T00:00:00Z"` |
| `string` (format: email) | `z.email()` | `"user@example.com"` |
| `string` (format: uuid) | `z.uuid()` | `"123e4567-e89b-12d3-..."` |
| `string` (format: uri) | `z.url()` | `"https://example.com"` |
| `string` (enum) | `z.enum([...])` | `"active"` |
| `allOf` | `Schema1.and(Schema2)` | Intersection |
| `oneOf` | `z.union([...])` | Union |
| `oneOf` (discriminator) | `z.discriminatedUnion(...)` | Discriminated union |

## Naming Conventions

The generator converts OpenAPI names to PascalCase:

- `user-profile` → `UserProfile`
- `api_key` → `ApiKey`
- `userSettings` → `UserSettings`

Special characters like `$` are preserved:

- `$special` → `$Special`

Collisions after normalization receive numeric suffixes (`User_1`). Generated exports
follow fixed patterns: `<Name>Model` for types, `parse<Name>` for validators.
